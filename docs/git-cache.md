# Git objects and repository packages

Format 4 accepts `subdir = "packages/math"` on a Git dependency. The selector is a portable repository-relative path: no absolute paths, backslashes, empty components, `.` or `..`. Its canonical destination must remain inside the selected checkout. Transitive paths are relative to that package's manifest. The lock records the repository commit and package subdirectory separately; compiler imports and metadata use the package directory. Older manifest formats remain unchanged. A new feature requires a version 4 lockfile; `--locked` never migrates an existing file.

Vex retains verified Git objects in a user cache and keeps complete, independent project checkouts. Linux and FreeBSD use `$XDG_CACHE_HOME/vex` (or `~/.cache/vex`), macOS uses `~/Library/Caches/vex`, and Windows uses `%LOCALAPPDATA%/vex`. Set an absolute `VEX_CACHE_HOME` to override the root. Repository declarations, including their authentication context, are hashed into opaque directory names. Credentials are never stored in cache configuration or diagnostics. Different authentication declarations do not share a cache entry.

A locked object missing from a checkout can be restored from this cache, including with `--offline`. The lockfile is authoritative: Vex never substitutes a branch tip for an unavailable commit. Unlocked branch selection and explicit updates still contact the source. Repeated packages from the same repository selection share a command-local commit snapshot. Local imports disallow network protocols even if Git URL rewrites are configured. No project checkout uses hardlinks or object alternates into the cache.

The project lease is acquired before a repository cache lease. Persistent OS coordination locks are never deleted as stale PID files. Cache candidates are copied, verified with Git, synced and atomically published. Corrupt entries are quarantined; an online command can repopulate them, while an offline command fails if no exact object remains. Quarantines are preserved for inspection. Dry-run and metadata do not restore checkouts or repair caches.

`vex cache prune` previews removal of recognized bare repositories; `vex cache prune --apply` removes them under their cache leases. It preserves coordination files, quarantines and unknown entries. Project checkouts remain usable afterward, but recreating one can require network access. There is no automatic cache GC. To investigate a quarantined entry, preserve it separately before manual removal; do not remove cache coordination files while Vex processes are running.
